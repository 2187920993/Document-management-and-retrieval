# 代码提交规范

文档编号：ENG-014  
版本：2.1  
维护团队：研发效能组  
生效日期：2026-09-10  
适用范围：星桥协作平台的前端、API 和后台任务服务

## 1. 目的与边界

本文约定开发者把修改交给同事审阅之前必须完成的准备。合并代码不代表可以立即上线；生产变更还需要执行《发布检查清单》。纯文案修订可以简化测试范围，但必须在合并请求中说明理由。

## 2. 从任务到分支

每项修改关联一个任务编号，例如 DOC-238。分支名称使用 feat/DOC-238-search-filter、fix/DOC-241-upload-retry 等形式。一个合并请求只解决一个清晰的问题，避免把格式整理、依赖升级和业务修复混在一起。开始前确认目标分支以及与其他同事的文件分工，禁止覆盖他人尚未提交的修改。

需要更改接口时，先在请求中写明旧行为和新行为。增加返回字段通常容易兼容；删除字段、改变字段含义和改变状态码需要列出受影响的调用方，并确定迁移顺序。

## 3. 交给审阅者之前

依次完成格式检查、静态检查、受影响模块的自动化测试和本地构建。涉及上传、权限、索引或数据库时，至少覆盖一个成功案例和一个失败案例。不要只证明按钮能点击，要确认接口返回值与数据库最终状态一致。

前端改动附上桌面和窄屏截图。后台任务改动说明重复执行是否安全、失败后如何重试。修改数据库结构时同时提交迁移脚本，说明已有数据如何保留、旧版本能否继续运行；破坏性变更不得假设所有服务会同时升级。

若某项检查未执行，应写出具体原因和未验证范围。不能把“代码看起来没有问题”填写成测试通过。

## 4. 合并请求应包含的内容

- 关联任务：任务编号和要解决的用户问题。
- 行为变化：一个具体的操作示例，以及改动前后的结果。
- 验证证据：实际执行的命令、结果或可复现操作。
- 风险与恢复：可能影响的接口、数据和必要的恢复步骤。
- 来源说明：使用开源代码或编码 Agent 的部分，以及人工核查的重点。

提交说明采用 feat:、fix:、docs: 等简短前缀，正文解释原因，不堆砌文件名。最终合并前同步目标分支，解决冲突后重新运行受影响的检查。由至少一名非作者完成审阅后合并；作者仍对最终结果负责。

## 5. 文件与敏感配置

数据库密码、对象存储密钥、访问令牌和真实用户资料不得进入仓库。提交前检查新增文件清单，尤其是 .env、日志、临时导出和截图。示例配置只写字段名或无效示例值。需要大文件时使用约定的资料位置，在仓库中记录引用和用途。

## 6. 一次容易混淆的操作

某同事通过了所有本地测试，将修复合并到 main。此时状态应是“等待发布”，并非“生产已生效”。执行部署、检查服务健康和验证实际业务属于发布步骤，详见文档 OPS-021。
