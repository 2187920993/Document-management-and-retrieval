本地部署故障排查
文档编号：RUN-008
版本：1.3
维护团队：平台运维组
更新日期：2026-09-17
适用环境：星桥协作平台 Docker Compose 演示部署

一、先确认失败发生在哪一层
不要在看到网页打不开后立即重建数据库。先检查容器状态和最近日志，再判断是端口、环境配置、服务依赖还是业务接口的问题。记录出现问题的操作与时间，不把数据库密码或访问令牌粘贴到问题描述中。

本项目服务名约定为 web、api、worker、db。先执行 docker compose ps 查看状态，再用 docker compose logs --tail=100 api 或对应服务名查看近期日志。容器在线只说明进程存活，仍需访问健康接口并执行一次业务操作。

二、浏览器打不开页面
如果日志提示地址已占用，检查宿主机映射端口是否被其他进程使用。修改宿主机端口后，也要核对 README 中的访问地址。不要把容器内部 api:3000 当作浏览器可以直接打开的宿主机地址。

若页面能打开但接口失败，查看前端配置的 API 地址，以及浏览器是否请求到了错误的主机。变更前端构建时注入的配置后，可能需要重新构建前端镜像；只重启现有容器不一定改变已经生成的静态资源。

三、容器重建后资料不见了
先核对数据库和上传目录是否挂载了具名卷或明确的宿主机目录。没有挂载的容器可写层不能承担持久化资料存储。还要检查是否更改了 Compose 项目名称，导致应用连接了另一组新数据卷。

不要立即运行带 -v 的清理命令，也不要删除旧卷。先记录 docker volume ls 的结果，确认旧数据所在位置，再按原项目名称和卷映射恢复连接。删除数据卷会同时删除其中的数据，重建镜像无法恢复这些内容。

四、数据库健康但 API 仍连接失败
核对 API 使用的是 Compose 网络内的数据库服务名、数据库名和配置字段。首次初始化数据库时设置的账号配置，通常不会因为修改应用环境文件就自动同步到已有数据库。需要检查实际连接错误，不要反复重置数据目录。

五、文件保存成功但一直不能搜索
检查 worker 是否启动、是否连接了与 API 相同的队列，以及索引任务的状态和失败原因。若使用外部向量服务，检查地址、网络和配置，不在日志中打印密钥。定位到索引故障后优先重新处理已有文档，避免让用户重复上传。

九月十八日的发布记录属于队列配置不一致；九月二十一日的复盘属于内容提取响应变化。相同界面现象可能对应不同原因，应依据处理阶段区分。

六、交付前复核
完成一次上传和下载，在正常保留数据卷的前提下重新创建应用容器，再核对原有文件、分类与检索结果。记录验证方式。仅提供一张启动成功截图，不能证明数据可以持久保存。
